What this is

A shop-level web tool that helps a repair shop write clearer customer notes, convert imported repair estimates into quotes, and protect monthly operations data — running entirely from a USB drive without online accounts.

What this is not

It does not replace Mitchell, diagnose cars, send estimates to customers over the internet, or connect to the shop’s accounting system unless later redesigned. That boundary is intentional.

Source tree: app/ estimate_conversion/ Llamafile/ Models/ runtime/

There are a few parts, but the main loop is simple: a user does something in a browser page, the server translates that action into work for an AI model, and the result comes back to the page. Most files in app/ exist to make that loop safe, fast, and predictable.

2. The Engines Inside the App

Translation engines

  • Tech translator — turns rough mechanic notes into customer-facing wording.
  • Advisor translator — same idea, but for advisor/customer text lines.
  • Intake translator — turns customer symptom text into a clean RO concern.
  • Quality checkers — score note clarity before translation.

Conversion / admin engines

  • Estimate converter — reads Mitchell PDFs, routes them through an AI estimate pipeline, outputs quotes.
  • BG coverage — local rules lookup for service contracts.
  • Operations digest — monthly report generation with a manager passcode.
  • Knowledge / cases — lookup approved translation examples.

Infrastructure engines

  • Model client — one gateway that supports Llamafile or Ollama with retry shaping.
  • Prompt templates — strict JSON envelopes that keep output consistent.
  • Network guard + upload security — loopback enforcement, file limits, correlation IDs.
  • Self-cleaning + logging — age-based file purge and structured request tracing.

4. The Browser ↔ Server Contract

FastAPI is just the surface. Each page/function lives in app/routes.py and calls smaller engines it imports at the top.

routes.py → app/model_client.generate(...)
         → app/prompt_templates.build_translation_prompt(...)
         → app/normalizer.normalize_translation_response(...)
         → app/database.save_translation(...)

routes.py → app/estimate_conversion.run_estimate_conversion(...)
         → subprocess.run(["python scripts/parse_mitchell_pdf.py ..."])
         → app/routes: resolve_output_pdf(...)

Why split files?

Routes handle browser behavior — pages and JSON responses. Engines handle one specific behavior — prompts, network calls, PDF parsing. If one engine breaks, the rest can keep running.

Why correlation IDs?

Every request gets an ID. If something breaks, the same ID appears in logs, so you can retrace one customer-facing action end to end.

6. Why “Customer Explanation” is hard

A technician writes notes under time pressure — short, abbreviated, sometimes wrong. A customer-facing sentence cannot contain that noise, or safety-adjacent confusion.

Raw note

“R&R RR axle seal, cleaned bpads, road test ok. LF strut noisy, check.”

System behavior

The rules tell the model to keep confirmed facts, preserve “check” as a recommendation rather than a repair, and never invent torque specs, prices, or a “safe to drive” guarantee the note never wrote.

Real safety property

The app isn’t trying to be clever. It is trying to be bounded. Most heavy logic is decreasing the chance of an AI sentence creating legal, safety, or warranty exposure on a customer invoice.

Implementation: app/prompt_templates.py → app/normalizer.py → app/note_quality.py

9. Why the Conversion Uses a Subprocess

Constraint

The Mitchell PDF pipeline was already a standalone Python script before this server app existed. Reusing it as an already-tested tool is the small, correct step.

Safety

The app wraps it with validation: mode whitelist, file existence checks, single conversion slot, timeout, and an import record so every run is auditable.

conversion_slot = BoundedSemaphore(value=1)

allowed modes: preestimate | quote | proposal

if provider == "llamafile" and mode in {"quote","proposal"}:
    require estimator online

11. Why Local Models

Data boundary

Customer vehicle information, labor notes, and ROS never leave the USB drive when running loopback-only. This is a compliance property, not just preference.

Cost and dependency

No API keys, no tokens, no account limits. The drive is self-contained; installers and wheelhouses are bundled.

Tradeoff

Running on CPU/Llamafile means the model is small: 4B and 3B parameters by design. Prompt discipline carries more weight than model size. That’s why the JSON envelope and rules are strict.

12. Security Constraints That Shape Behavior

  • Loopback only — rejects any client that is not from 127.0.0.1. That means no default “open from phone” shortcut without a separate, explicit redesign.
  • Host-header rejection — blocks non-loopback host headers.
  • CSRF style guard — expect state-changing browser POSTs to require appropriate origin.
  • Operations pin — 2470 manager code gates the operations digest APIs.
  • Upload restrictions — PDF size bound, optional delete-after-run, temporary workspace, no arbitrary directory write.

Implementation: app/network_guard.py app/upload_security.py app/routes.py

13. PDF Parsing and Output Path

Conversion does not invent PDF generation inline for line items. It reuses the bundled Mitchell parser and adds document assembly on top.

 ├── sanity_confirmed check
 └── outputs state importable to PDF/print

Outputs:
   • front-end quote PDF via reportlab
   • runtime/import_records/*.json for audit

Bundled tools

reportlab builds branded PDFs. pdftotext from Poppler extracts readable text. Both are either bundled, installed offline, or rejected by readiness checks.

14. Background Safety Systems

Cleanup thread

Starts on server boot. Removes logs older than 14 days, orphan uploads older than 1 day, and old import records after 30 days.

Preflight checks

Before any quote PDF is built, the system flags parts-without-labor, misplaced steering parts, and duplicate/split lines so the advisor can correct the estimate before it becomes a customer document.

16. Get from A to B: A Real Example

A service advisor clicks “Convert to Quote” for an uploaded Mitchell PDF at /estimate-conversion.

1. Browser sends form + PDF path to /api/estimate-conversion
2. app/routes.py calls run_estimate_conversion()
3. run_estimate_conversion():
     • acquires conversion_slot
     • reads input PDF from workspace uploads
     • runs parse_mitchell_pdf.py via subprocess
       with mode=preestimate and the shared Qwen3 model on 8080
     • captures stdout → extracts final PDF path
     • releases slot
4. Routes returns JSON with output PDF path and report file
5. Browser enables “Download Quote PDF” button

Only one quote runs at a time to protect that single model slot from parallel overload.

17. Loops, Bounded Concurrency, and Retries

Semaphores

Translation has a queue lock and boolean guard; estimate conversion has a bounded semaphore. Both prevent concurrent writes into the same model socket.

Not magical, protective

The app trades throughput for predictability. One conversion at a time is still fast enough and avoids corrupting the estimator output.

_queue_lock = threading.Lock()
_queue_is_processing = False

_conversion_slot = threading.BoundedSemaphore(value=1)

if not _conversion_slot.acquire(blocking=False):
    raise RuntimeError("Another estimate conversion is already running.")

19. Summary

What the app does well

It keeps customer-visible text safe, keeps data local, and runs from removable media with fixed offline dependencies. It avoids the usual web-app risks: cloud exposure, mystery runtime, dependency drift.

Where it stays narrow

It does not manage Mitchell state, scheduling, parts inventory, or customer billing. That architectural choice keeps review scope small and shipping velocity high.

The mental model

Blueprints over features. The app is several small engines connected by routes — translation engine, conversion engine, BG rules, operations digest, case library — not one giant bundle of AI logic. That is why it can be explained, reviewed, and verified.
